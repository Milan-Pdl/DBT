In dbt, the analyses/ folder is a dedicated space for writing analytical SQL queries that you want to version control, but you don't want dbt to build as tables or views in your data warehouse.

Think of it as a scratchpad for your data team. It allows you to use all of dbt's powerful features (like {{ ref() }} and macros) to write complex queries without cluttering your production database schemas.

Why use the Analyses folder? (The Core Benefits)
If you just run a standard SELECT query in an SQL client, you lose the ability to reference modular models or use Jinja. By placing those same queries inside the analyses/ directory, you get the best of both worlds:

Use of the {{ ref() }} function: You can safely query your clean Silver or Gold models without hardcoding database and schema names.

Jinja & Macros: You can use your custom macros or conditional logic inside these files.

Version Control: Your ad-hoc scripts, audit queries, and one-off reports are saved in Git right alongside your core data pipeline.

Common Use Cases for Analyses
You should use the analyses/ folder for queries that are useful to save, but shouldn't live permanently as data warehouse relations:

Ad-hoc Stakeholder Requests: A manager asks for a quick, one-time pull of sales data for a specific marketing campaign over the last weekend.

Data Auditing & Validation: Complex queries you run manually to check for data discrepancies between systems before a major launch.

Complex Dashboard SQL Backing: Writing and testing the heavy SQL logic that you intend to copy-paste directly into a BI tool (like Tableau, Power BI, or Looker Studio) that doesn't support direct dbt references.

How to use it
1. Create a .sql file
Create a file inside your analyses/ directory, for example: analyses/campaign_performance_audit.sql.

2. Write your query using ref()
SQL
-- analyses/campaign_performance_audit.sql
select 
    store_sk,
    sum(gross_amount) as total_gross
from {{ ref('bronze_dim_sales') }}
where gross_amount > 1000
group by 1
3. Compile the query
When you run a standard dbt run, dbt will completely ignore this folder. To compile this query into raw, executable SQL, run:

Bash
dbt compile
4. Find your executable SQL
dbt will parse your Jinja code and generate a clean, copy-pasteable SQL file inside your project's target directory:
target/compiled/DbtPratice/analyses/campaign_performance_audit.sql

If you open that compiled file, you will find that {{ ref('bronze_dim_sales') }} has been perfectly translated into your actual Databricks path (e.g., hive_metastore.bronze.bronze_dim_sales), ready to be executed in your workspace!
